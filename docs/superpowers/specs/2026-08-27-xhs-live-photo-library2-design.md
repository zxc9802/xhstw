# 小红书 Live 实况照片完整保存设计

## 目标

让浏览器插件在小红书图文详情页中识别 Live 实况照片，并把每张 Live 的静态封面和对应动态 MP4 成对保存到当前登录账号的爆款选题库2。普通图片、标题、正文和原始顺序继续保留。

爆款裂变仍是图文流程：只把 Live 的静态封面带入图文生产，动态视频仅用于爆款选题库2中的完整归档与播放。

## 非目标

- 不把 Live 视频送入视频脚本或视频生成流程。
- 不支持小红书直播间、普通视频笔记或 TikTok/Douyin 的类似动态照片格式。
- 不迁移或重写既有爆款选题库2数据。
- 不改变普通小红书、抖音和 TikTok 图文的上传行为。

## 已验证的页面结构

在公开 Live 笔记 `6a8f682f000000002503f464` 上验证到：

- 每张 Live 的可见容器为 `.live-photo-contain`。
- 静态封面由 `.live-img` 提供。
- 动态部分显示为 `.live-video`，DOM 中的 `src` 是页面生成的 `blob:` 地址。
- 页面在轮播到对应图片时，才通过 `fetch` 请求 `sns-video-*.xhscdn.com/...mp4`。
- 当前页未激活时，其 MP4 可能尚未出现在页面资源记录里。
- Swiper 会生成重复幻灯片，不能按 DOM 节点数量直接计算素材数量。

因此采集不能只扫描一次 DOM，也不能把 `blob:` 地址交给扩展后台下载；必须逐页激活轮播、捕获对应的远程 MP4，并按封面去重和配对。

## 方案选择

采用“封面与视频成对保存”。

未采用的方案：

- 把所有 MP4 当独立附件保存：无法可靠知道视频对应哪张封面，预览和删除容易错位。
- 把整篇 Live 打成 ZIP：不能在爆款选题库2中直接播放，也不利于图文裂变复用静态封面。

## 数据模型

保留现有 `Library2Item.images` 数组，Live 静态封面仍是一张普通图片，因而旧页面和图文裂变天然兼容。

新增可选字段：

```ts
interface Library2LivePhoto {
  order: number;
  coverFileId: string;
  videoFileId: string;
  key: string;
  contentType: "video/mp4";
  size: number;
}

interface Library2Item {
  // 现有字段不变
  images: Library2Image[];
  livePhotos?: Library2LivePhoto[];
}
```

约束：

- `order` 对应原作品图片顺序，从 0 开始。
- `coverFileId` 必须引用同一条内容中的一张 `images`。
- 每个封面最多关联一个 Live 视频。
- 普通图片不出现在 `livePhotos` 中。
- 该字段可选，旧数据无需迁移；旧客户端会忽略新增字段。

## COS 对象路径

继续使用当前账号的 `ownerId` 隔离：

```text
users/<ownerId>/library2/<contentId>/manifest.json
users/<ownerId>/library2/<contentId>/images/<coverFileId>
users/<ownerId>/library2/<contentId>/live/<videoFileId>.mp4
```

列表、读取、播放、删除都必须从登录会话或插件 Bearer Token 解析 `ownerId`，不能接收客户端自行指定的账号 ID。

## 插件采集流程

1. 用户在小红书详情页点击“上传资料库”。
2. 插件读取真实轮播总数和当前页，不使用 Swiper 重复节点计数。
3. 从第一张开始逐页激活轮播，并在每页稳定后读取静态封面。
4. 普通图片只记录封面 URL。
5. Live 图片等待 `.live-video` 出现，同时从 Resource Timing/PerformanceObserver 中获取该页触发的 `xhscdn` MP4 地址。
6. 按规范化封面 URL 去重，记录 `{ order, coverUrl, videoUrl }`。
7. 完成后恢复用户原来查看的轮播页。
8. 在申请上传地址前，先下载并校验全部图片和 Live 视频，避免形成可见的半条内容。
9. 申请同一个 `contentId` 下的图片和 Live 视频上传地址，逐个上传后一次性提交 manifest。

若 Resource Timing 没有可用的远程 MP4，而当前 `<video>` 只有 `blob:` 地址，则由内容脚本读取该 `blob:` 字节，并复用扩展已有的分块媒体传输机制交给后台；不能把页面专属 `blob:` 地址直接交给 Service Worker。

## 上传与校验

- Live 动态格式第一期只接受 `video/mp4`。
- 通过响应头和 MP4 `ftyp` 文件签名共同校验，不能只信 URL 后缀。
- 最多保持现有的 20 张图片上限，每张图片最多一个 Live 视频。
- 单个 Live 视频最大 100 MB，单条内容 Live 视频总量最大 500 MB。
- 普通图片在保持原顺序的前提下，最多 4 张并发上传到工作台，任一失败时报告原始图片序号。
- Live 视频按顺序下载和上传，避免多个大文件同时占用浏览器内存。
- 远程媒体地址继续限定为小红书和 `xhscdn.com` 的 HTTPS 主机。
- 服务端提交时重新校验上传对象、账号、对象路径、类型、大小和封面引用关系。

## 完整性与错误处理

“完整保存”的成功标准是：所有普通图片、所有 Live 静态封面、所有 Live MP4、标题和正文均已上传并写入同一个 manifest。

- 任意 Live 页面在限定时间内没有取得 MP4：停止提交，底栏明确显示第几张 Live 获取失败。
- 图片或视频下载失败：停止提交，不创建爆款选题库2条目。
- 上传失败：停止提交，不写 manifest；显示具体媒体序号和类型。
- 配对数量或顺序不一致：服务端拒绝提交。
- 普通图片笔记和不含 Live 的旧流程不受影响。

## 爆款选题库2界面

- Live 封面卡片左上角显示 `LIVE` 标记。
- 点击普通图片继续打开图片预览。
- 点击 Live 封面打开视频预览，以静态封面作为 poster，MP4 支持播放、暂停、静音和循环。
- 删除 Live 封面时同时删除关联 MP4，并更新 manifest。
- 删除整条内容时删除全部图片、Live 视频和 manifest。
- 图片数量仍按原作品图片张数显示，Live MP4 不额外计为一张图片。

## 图文裂变

`library2PrefillPayload` 继续只遍历 `images`：

- Live 静态封面与普通图片按原顺序进入参考素材池。
- `livePhotos` 中的 MP4 不进入图文生产，也不触发视频流程。
- 标题、正文、平台和来源链接的现有预填逻辑保持不变。

## 浏览器兼容

实现只使用 Manifest V3、标准 DOM、PerformanceObserver、Fetch 和现有扩展消息机制，目标覆盖 Chrome 与 Edge。安装或更新插件后仍需刷新已打开的小红书页面，并允许插件访问小红书站点。

## 测试设计

### 插件单元与页面夹具

- 三页混合轮播：Live、普通图片、Live，验证顺序和两个配对。
- Swiper 重复节点不会造成重复图片或重复视频。
- Live MP4 延迟加载时会等待对应资源，而不是拿到上一页视频。
- 当前页初始不是第一页时，采集完成后恢复原页。
- 只有封面没有 MP4 时整条上传失败。
- `blob:` 回退路径按块传输完整 MP4。
- 普通图文现有提取结果保持不变。
- 普通图片上传并发峰值为 4，完成后的提交顺序仍与原作品一致。

### 服务端与存储

- 上传意图生成账号隔离的图片和 Live 视频对象路径。
- 拒绝非 MP4、超限视频、重复配对和跨内容封面引用。
- manifest 只在全部媒体存在且匹配时提交。
- 读取和删除不能访问其他账号的 Live 媒体。
- 删除 Live 封面会同时删除关联视频。

### 页面与裂变

- Live 封面显示标记并能打开同账号的视频流。
- 旧数据不含 `livePhotos` 时正常渲染。
- 裂变预填只包含静态封面，不包含 MP4。
- 插件打包测试覆盖新增文件，并将发布版本提升到下一个补丁版本。

## 验收标准

1. 在 Chrome 和 Edge 打开含普通图片与 Live 的小红书详情页，插件显示正确的原图片数量。
2. 上传成功后，爆款选题库2的图片数量、顺序和原作品一致。
3. 每张 Live 封面都有 `LIVE` 标记，点击可播放对应动态视频，不串页、不重复。
4. 数据存入当前账号的 COS 前缀，其他账号无法读取。
5. 点击爆款裂变后只带入静态封面、标题和正文。
6. 任一 Live 视频缺失时上传明确失败，不出现残缺库条目。
7. 普通小红书、抖音和 TikTok 图文上传回归测试全部通过。
